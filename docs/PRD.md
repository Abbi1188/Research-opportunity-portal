## 1. Overview

### 1.1 Problem
The university shares research opportunities through emails, WhatsApp groups, and noticeboards. Information is scattered, so students miss opportunities and faculty find it hard to manage their openings.

### 1.2 Solution
A web-based **Research Opportunity Portal** where faculty members can **post, view, update, and manage** research opportunities in one place. It has three parts:
1. A backend REST API
2. A MySQL database
3. A simple frontend interface

### 1.3 Goals
- Keep all research opportunities in one place.
- Let faculty create, read, update, and delete (CRUD) opportunities.
- Let faculty close an opportunity when it is no longer open.
- Provide a simple, clean, working interface.
- Prove the API works using Postman.

### 1.4 Non-Goals (out of scope)
Only what the assignment asks for is built. These are **not** included: login/accounts, student applications, search or filters, file uploads, email notifications, or an advanced UI.

## 3. Data Model

**Database:** `research_portal`  **Table:** `opportunities`

| Field                 | DB column              | Type                  | Required | Rules                                   |
|-----------------------|------------------------|-----------------------|----------|-----------------------------------------|
| Unique ID             | `id`                   | INT, auto-increment, PK | auto   | Generated by the database               |
| Research title        | `title`                | VARCHAR(255)          | Yes      | Not empty                               |
| Research description  | `description`          | TEXT                  | Yes      | Not empty                               |
| Research area         | `research_area`        | VARCHAR(150)          | Yes      | Not empty                               |
| Faculty member's name | `faculty_name`         | VARCHAR(150)          | Yes      | Not empty                               |
| Department            | `department`           | VARCHAR(150)          | Yes      | Not empty                               |
| Required skills       | `required_skills`      | VARCHAR(500)          | Yes      | Not empty (comma separated text)        |
| Available positions   | `available_positions`  | INT                   | Yes      | Whole number, at least 1                |
| Application deadline  | `application_deadline` | DATE                  | Yes      | Valid date, format `YYYY-MM-DD`         |
| Status                | `status`               | ENUM('Open','Closed') | No       | Only `Open` or `Closed`; default `Open` |

Setup script: `database/schema.sql`. All CRUD operations must use this database. **No hard-coded data anywhere.**

## 4. Backend Requirements (REST API)

Base URL: `http://localhost:5000/api`
Format: JSON requests and JSON responses (`Content-Type: application/json`).

### 4.1 Endpoint Summary

| ID   | Operation                     | Method | URL                       | Success code |
|------|-------------------------------|--------|---------------------------|--------------|
| API-1| Create a research opportunity | POST   | /api/opportunities        | 201          |
| API-2| Retrieve all opportunities    | GET    | /api/opportunities        | 200          |
| API-3| Retrieve one opportunity      | GET    | /api/opportunities/:id    | 200          |
| API-4| Update a research opportunity | PUT    | /api/opportunities/:id    | 200          |
| API-5| Delete a research opportunity | DELETE | /api/opportunities/:id    | 200          |

### 4.2 Response Format (keep this consistent)

Success:
```json
{ "message": "Opportunity created successfully", "data": { ...record or list... } }
```
Error:
```json
{ "error": "Title is required" }
```
For the create response, `data` is the full saved record including its new `id`. Postman reads `data.id` to save the ID for later requests.

### 4.3 API-1 Create
- **Request body:** all required fields from section 3 (`status` optional, defaults to `Open`).
- **201** – saved; returns the new record.
- **400** – any required field is missing or invalid.
- **500** – database or server error.

```json
{
  "title": "AI for Medical Imaging",
  "description": "Research on detecting diseases from medical scans.",
  "research_area": "Artificial Intelligence",
  "faculty_name": "Dr. Ayesha Khan",
  "department": "Computer Science",
  "required_skills": "Python, Machine Learning",
  "available_positions": 2,
  "application_deadline": "2026-12-15",
  "status": "Open"
}
```

### 4.4 API-2 Get All
- **200** – returns an array of all opportunities (empty array `[]` if none).
- Newest first (order by `id` descending).
- **500** – database or server error.

### 4.5 API-3 Get One
- **200** – returns the complete record for the ID.
- **400** – ID is not a positive whole number.
- **404** – no opportunity with that ID. Error: `"Opportunity not found"`.
- **500** – database or server error.

### 4.6 API-4 Update
- Used to change the title, required skills, available positions, application deadline, status, or any other field.
- **Request body:** one or more fields from section 3. Any field sent must pass the same rules as create. Fields not sent stay unchanged.
- **200** – updated; returns the updated record.
- **400** – invalid ID, empty body, or an invalid field value.
- **404** – ID does not exist.
- **500** – database or server error.
- **Closing:** sending `"status": "Closed"` closes the opportunity.

### 4.7 API-5 Delete
- **200** – deleted; message `"Opportunity deleted successfully"`.
- **400** – invalid ID.
- **404** – ID does not exist (including when requested a second time).
- **500** – database or server error.

### 4.8 Status Codes Used

| Code | Meaning               | Used when                                  |
|------|-----------------------|--------------------------------------------|
| 200  | OK                    | Successful GET, PUT, DELETE                |
| 201  | Created               | Successful POST                            |
| 400  | Bad Request           | Missing/invalid data or invalid ID         |
| 404  | Not Found             | ID does not exist                          |
| 500  | Internal Server Error | Unexpected server/database error           |

### 4.9 Validation Rules (backend)
- All text fields must be present and not empty or only spaces.
- `available_positions` must be a whole number of 1 or more.
- `application_deadline` must be a valid date in `YYYY-MM-DD` format.
- `status` must be exactly `Open` or `Closed`.
- `:id` must be a positive whole number.
- Use parameterized queries (no string-joined SQL).

### 4.10 Backend Non-Functional Requirements
- Database login details are read from `.env` (never committed).
- The server starts with `npm start` on the port in `.env` (default 5000).
- Clear error messages; never expose database passwords or stack traces in responses.
- Code split into routes, controller, middleware, and config (see section 8).

## 5. Frontend Requirements

A **simple, clean, and functional** interface using HTML, CSS, JavaScript, and Bootstrap. It talks to the backend only through the REST API and **never hard-codes data**.

### 5.1 Functional Requirements

| ID   | Requirement                                              | How it works                                                       |
|------|----------------------------------------------------------|--------------------------------------------------------------------|
| FE-1 | Display all available research opportunities             | On page load, call `GET /api/opportunities` and show cards         |
| FE-2 | Display complete details of a selected opportunity       | "View" button calls `GET /api/opportunities/:id` and shows a modal |
| FE-3 | Form for creating a new opportunity                      | "Add Opportunity" button opens a form, submit calls `POST`         |
| FE-4 | Option to update an existing opportunity                 | "Edit" button fills the form, submit calls `PUT`                   |
| FE-5 | Change status from Open to Closed                        | "Close" button calls `PUT` with `status: "Closed"`                 |
| FE-6 | Option to delete an opportunity                          | "Delete" button, after confirmation, calls `DELETE`                |
| FE-7 | Appropriate success and error messages                   | Bootstrap alerts after every action                                |
| FE-8 | Basic validation of required form fields                 | Checked in the browser before the request is sent                  |

### 5.2 Page Layout (single page `index.html`)
1. **Navbar** – title "University Research Opportunity Portal" and an "Add Opportunity" button.
2. **Message area** – Bootstrap alert (green success, red error) that hides after a few seconds.
3. **Opportunities list** – responsive Bootstrap cards. Each card shows title, research area, faculty name, department, positions, deadline, and a status badge.
4. **Card buttons** – View, Edit, Close (only shown when status is Open), Delete.
5. **Details modal** – all fields of one opportunity.
6. **Form modal** – used for both create and edit.
7. **Delete confirmation** – confirm before deleting.
8. **Empty state** – message "No research opportunities found" when the list is empty.

### 5.3 Design Guidelines
- Bootstrap 5 for grid, cards, forms, buttons, badges, modals, alerts.
- Light background, one primary button color, readable fonts.
- Status badge: **Open = green**, **Closed = grey**.
- Works on phone and desktop (responsive grid).
- `style.css` holds only small tweaks.

### 5.4 Frontend Validation Rules
- Title, description, research area, faculty name, department, and required skills must not be empty.
- Available positions must be a number of 1 or more.
- Application deadline must be selected.
- Status must be Open or Closed.
- Invalid fields show Bootstrap's invalid style and a short message. Backend errors (400/404/500) are also shown in the message area.

### 5.5 Messages

| Action          | Success message                       | Error message                                |
|-----------------|---------------------------------------|----------------------------------------------|
| Create          | Opportunity created successfully      | Message from backend or "Could not create"   |
| Update          | Opportunity updated successfully      | Message from backend or "Could not update"   |
| Close           | Opportunity closed successfully       | Message from backend or "Could not close"    |
| Delete          | Opportunity deleted successfully      | Message from backend or "Could not delete"   |
| Load list       | –                                     | "Could not load opportunities"               |
| Backend offline | –                                     | "Cannot connect to the server"               |

## 6. Postman Testing Requirements

The backend must be tested with Postman. Collection file: `postman/Research_Opportunity_Portal.postman_collection.json`. Variable `baseUrl` = `http://localhost:5000/api`.

| #  | Test                                    | Request                      | Expected result |
|----|-----------------------------------------|------------------------------|-----------------|
| 1  | Create opportunity 1                    | POST /opportunities          | 201             |
| 2  | Create opportunity 2                    | POST /opportunities          | 201             |
| 3  | Create opportunity 3                    | POST /opportunities          | 201             |
| 4  | Retrieve all                            | GET /opportunities           | 200, list contains the 3 records |
| 5  | Retrieve one by ID                      | GET /opportunities/{{id1}}   | 200             |
| 6  | Update an opportunity                   | PUT /opportunities/{{id1}}   | 200, new values returned |
| 7  | Change status Open to Closed            | PUT /opportunities/{{id2}}   | 200, status = Closed |
| 8  | Delete an opportunity                   | DELETE /opportunities/{{id3}}| 200             |
| 9  | Request the deleted one again           | GET /opportunities/{{id3}}   | 404             |
| 10 | Send invalid or missing data            | POST /opportunities          | 400             |

Notes:
- Run the requests in order. Requests 1–3 save `id1`, `id2`, `id3` automatically from `data.id`.
- Each request has a test script that checks the status code.
- Export the final collection (Collection v2.1) and include it in `postman/`, GitHub, and the ZIP.
